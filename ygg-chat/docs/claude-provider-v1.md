# Claude Code provider v1

Claude Code is a separate main-chat execution backend. The Agent SDK drives the installed host CLI; Claude owns model execution, tools, native transcript and compaction. Graviton stores a display projection in the existing message/lineage tree and serves its existing streaming/Heimdall interface. Other providers still use ToolLoopService. Graviton tools and context loader are not injected into Claude sessions. Configured Graviton Stop hooks run host-side after successful response persistence; they are not injected as native SDK hooks.

## Start and continue

Install Claude Code on the host and complete its login in a terminal. Select **Claude Code**, select Haiku/Sonnet/Opus 5.5, and choose a workspace folder before the first send. An explicit `CLAUDE_BRIDGE_BINARY` can select the installed executable. No Graviton token collection or OAuth-token extraction is used. The CLI's authentication/provider environment determines billing; an inherited `ANTHROPIC_API_KEY` may select API billing. Account eligibility and third-party usage terms still apply.

After the first accepted user row, the provider is fixed on inherited ancestry; forks retaining that history inherit it. The provider control is disabled and server admission validates persisted ancestry. The Claude model is not part of the lock: it may change between turns (behind the normal model-switch confirmation), and the native session resumes or forks under the newly selected Claude model. Switching to a smaller-context model on a long transcript leaves overflow handling to Claude. **Branch on the first real user prompt** is a clean-start exception: the editor may choose Claude or another provider/model in either direction, creating an independent execution branch inside the same conversation. Only known launch context/settings notices may precede that prompt; hidden tool activity, compaction and earlier conversation are not clean starts. The new branch drops the source launch scaffolding, starts a fresh Claude session or generates fresh Graviton context for the selected provider, and preserves the original messages/session. Editor choices are discarded on cancel/navigation. Existing raw mid-conversation provider history cannot be imported into Claude. A committed compaction summary is a second explicit handoff boundary: **Branch from summary** accepts a new request/provider/model, creates an independent execution lineage/session, and transfers only summary text with fresh target-provider setup. The normal composer also permits crossing the Claude boundary immediately after a summary in either direction (Claude after a non-Claude summary, or another provider after a Claude summary), including through restored context/settings notices; its next send uses the same explicit summary-branch route. Staying in the same provider family continues ordinarily (a Claude summary keeps its native session). Any subsequent real user/assistant activity closes that composer handoff window. Editing/retrying the first prompt after a summary preserves that handoff. Source messages/sessions are unchanged. Workspace remains fixed per native branch.

SDK `forkSession(session, { upToMessageId })` creates an independent historical session. Shared ancestors remain shared Graviton nodes, with source session/message checkpoint mappings. Only successful completed-turn response checkpoints are resumable/forkable in v1. Root user edit starts a fresh native session with the editor's selected identity; repeat retains inherited identity. Arbitrary tool-block or partial-output cuts are refused instead of silently importing a different context. Native forks do not undo workspace side effects.

Session data is required for continuation; deleting it leaves the Graviton display copy readable but cannot silently start a replacement. Failed/interrupted native execution is marked uncertain; fork from a completed ancestor to recover. Startup-lost `running` state is also treated as uncertain. No external terminal sessions are attached automatically.

## Reasoning slider

The composer reasoning slider applies on each new turn, including continuation and forks. Low, Medium, High and X-High pass the matching SDK `effort` with adaptive thinking; Off explicitly disables extended thinking. Effort, like the model, is not part of the branch's locked provider identity and can change between turns, not during a running turn. Callers omitting both reasoning settings retain Claude's native default. Model/account support and any native effort downgrades remain Claude-owned.

## Tools and permissions

Claude uses its native tools, not Graviton's tool registry or subagent engine. SDK permission requests are routed through DecisionBroker and the existing stream-specific approval UI. Claude permission mode is `default`, or `auto` when the composer approval control is set to Auto (Claude only: Ask → Auto → Allow all; Auto is sent only while Allow all is off, so calls the classifier cannot decide still prompt, and a `claude_auto_unavailable` notice is emitted if the CLI falls back). Chat mode is not native plan mode: Claude can converse and use read/shell tools under the normal approval gate, while an SDK `PreToolUse` hook denies Edit/Write/MultiEdit/NotebookEdit/EnterPlanMode. Both modes send the same tool list. `disallowedTools` (or a bare deny rule) would remove tools from the request, and since tools lead the cached prefix, every mode switch would re-bill the whole transcript. The hook decision outranks Claude's own allow rules, `acceptEdits` and the auto classifier, and applies to child agents. Chat-mode messages end with a one-line note (`CHAT_MODE_NOTE`) that file edits, including through Bash, are disabled; it sits in the new user message, after the cached prefix, and is left off native commands. Bash writes are discouraged by that note, not blocked. A Claude run never persists a mode-notification row after its final response (one would displace the resumable checkpoint): the turn's mode is `meta.operationMode` on its user row and on each response row, and `Chat.tsx` derives the usual Chat/Agent notice below the first Claude user row of a branch and wherever the mode changes (`claudeModeNotices.ts`). The mode can also change during a run; see Live mode switches below. No SDK permission-bypass mode is enabled. Graviton's Ask / Allow all setting is captured at run start: `toolAutoApprove: false` prompts for native permission requests; otherwise the broker auto-approves them. Allow all on a pending permission persists the originating branch's approval policy before releasing current/future permission waits. Later messages on that branch retain it, including after reload/restart; other branches are not promoted. The composer Ask / Allow all control is branch-scoped. Historical forks inherit only at their cut; fresh summary/clean-start execution handoffs use the host default unless explicitly selected. Admission honors this policy instead of forcing Claude back to Ask on each run. Tools Claude considers safe may execute without prompting. AskUserQuestion is denied before approval handling, with instructions to ask in prose. In Chat mode, ExitPlanMode asks the user to switch to Agent mode; accepting switches the run's shared mode control, so the edit block lifts for the rest of the run and a queued successor run also starts in Agent mode. The host permission callback also denies the file-edit tools in Chat mode as a backstop, even with Allow all; everything else follows the approval gate.

Claude Code's own settings layers load as in the CLI (`settingSources: ['user', 'project', 'local']`): its skills, hooks, plugins, CLAUDE.md and permission rules apply, so a tool its `permissions.allow` covers runs without a Graviton prompt. MCP configuration stays empty/strict. Admin-managed policy/hooks remain Claude-owned. Native tools get a filtered environment, not Graviton's unrelated app credentials. This is not OS sandbox isolation.

Native hooks stream as `hook_started` / `hook_progress` / `hook_response` (`includeHookEvents`) and are stored as hook runs with `sourceFile: 'Claude Code'`: tool events on the row of the latest call to that tool, the rest on the current head (the user row for SessionStart/UserPromptSubmit). Exit 2 is recorded as a successful `blocked` outcome. A Skill call's instructions, which Claude adds as a synthetic user message, are kept as a `context_injection` block (`origin: 'claude'`) beside the call; Graviton never re-sends such blocks to Claude. Instruction files Claude loads itself (CLAUDE.md chain, `.claude/rules` including `paths:` matches, `@` imports) arrive through an SDK `InstructionsLoaded` callback and render through the same `ContextInjectionCard`: a load with a `trigger_file_path` sits beside the result of the Read/Edit/Write call on that path ("After step N"), other loads on the next assistant row, unclaimed loads on the final row. The text is read from disk without frontmatter or HTML comments, so it shows the current file, not a byte copy of the model's input. Each file shows once per run. Resumed/forked sessions skip untriggered startup loads, which the session showed when it started. Child-agent loads stay in Claude's transcript. Only the `Read`/`Edit` tools trigger path rules; Bash file access does not.

## Scope limits

- Text and selected-file context only; pasted image attachments are rejected.
- Queued user input and live Chat/Agent switches are supported (see Queued input and Live mode switches below). A manual `/compact` run refuses queued input but accepts a mode switch.
- `/compact` while idle resumes the selected native Claude session and invokes Claude’s own `/compact`. Graviton’s summarizer provider/model/prompt settings are not applied. Active-run manual compaction remains refused; native auto-compaction continues normally. A `/name` Graviton cannot expand is looked up in Claude's command list (a hook-less CLI that gets no prompt): user, project and plugin skills and custom commands lead the prompt for Claude to expand, and the user row records the command and its description (Claude does not stream the expanded body). Claude's built-ins are rejected. As in the CLI, input is a command only when the first word after `/` is a command name (`^[a-zA-Z0-9_][a-zA-Z0-9:_-]*$`, `parseClaudeSlashCommand`); a message that starts with a path such as `/Users/me/plan.md` is an ordinary prompt.
- No Graviton custom tools, REPL or subagent controls. Graviton Stop side-effect hooks run after a successful persisted response (sync/async commands and local API callbacks supported); other Graviton hook lifecycles and Stop-driven model continuation/context injection are not bridged. Failed/aborted runs and manual compaction skip Stop. Host-owned SDK compaction callbacks run beside Claude's own native hooks. Graviton runs recorded before their row exists (UserPromptSubmit, SessionStart, PreCompact) are attached to the user row or compaction summary once it is persisted.
- Native child details remain in Claude's own transcript; parent tool activity/results are projected.
- Direct content edits are rejected; use an edit branch. Notes remain editable. Deletion works like Claude Code's rewind: it cascades, so it cuts the branch back, and `planMessageDeletion` (`persistence/claudeMessageDeletion.ts`) allows the cut only where Claude can continue — at a resumable response checkpoint, at the conversation root, or beside a surviving sibling (for example a regenerated response). Launch scaffolding owned only by a deleted first prompt goes with it. Other cuts (a mid-turn queued message, the only response of a turn, the first prompt after a compaction summary) return 409 `claude_delete_refused`. The next send forks the native session at the checkpoint; an emptied branch loses its `claude_branch_sessions` row and starts fresh. Chat shows Delete on Claude user messages; Heimdall accepts any selection and the server validates it. Claude's native session files are never deleted, and workspace files are not restored.
- The displayed model list is a configured catalog, not verified account entitlement.
- Uses installed CLI plus version-pinned SDK `0.3.309`; no bundled CLI resolution relative to esbuild output.

## Queued input

The composer queues messages on a running Claude turn, through the same `MessageInputQueue` and queue routes as other providers. `ClaudeSessionService` keeps the SDK input stream open and pushes each entry with `priority: 'next'` and its own uuid. Before the push, the orchestrator runs UserPromptSubmit and renders hook context and selected files into the prompt (`claudeQueuedInput` in `chatOrchestrator.ts`). Claude decides when it reads the message:

- At its next tool boundary, the message joins the running turn. Claude sees "The user sent a new message while you were working".
- With no tool boundary left, the message starts a new turn after `result`. The session stays open until no queued entry remains.

The entry stays `queued`, and so cancellable, until Claude sends `command_lifecycle: started`. Only then does Graviton persist the user row, at the current head. The next assistant row is its child, so the tree shows where Claude actually read the message. The native transcript stores a mid-turn message as a `queued_command` attachment, and `getSessionMessages` shows it as a `user` entry with the same uuid.

DELETE on a held entry calls the SDK's `cancelAsyncMessage(uuid)`. This method exists in the pinned 0.3.309 runtime but not in its `.d.ts`, so the service checks for it first. The CLI answers `true`, and sends a `cancelled` lifecycle frame that can arrive first. A message Claude already started cannot be withdrawn; DELETE answers 409. If Claude does not start a held entry within 30 seconds of a turn's end, the entry fails and the run ends.

Limits: slash commands cannot be queued, because Claude would dispatch them as native commands. A manual `/compact` run refuses queued input, because it ends at its summary. Queued images use the same Claude format checks as a normal send. Full access never applies, so a queued `fullAccess` flag is dropped. The parent assistant row of a mid-turn message ends in a `tool_use`, so it stays non-resumable, the same as other tool-block cuts.

`scripts/test-claude-queue-live.mjs` (opt-in, `CLAUDE_PROVIDER_LIVE_TEST=1`) prints the raw SDK lifecycle and native transcript for `next`, `later`, post-result and cancel cases. The opt-in service test `live service: folds, defers and withdraws queued messages on the real CLI` checks the service path.

## Live mode switches

The Chat/Agent control works while a Claude run streams, through the same `POST /api/conversations/:id/operation-mode` route and `OperationModeControl` as other providers. The orchestrator passes the run's control to `ClaudeSessionService`. During a manual `/compact` run the switch waits, like a queued message: the run has no turn to carry it, so the committed summary row records it in `meta.operationMode` (every summary records the mode it ended in). The composer restores that mode and the next send uses it. Graviton providers already accept a switch during manual compaction and persist the `operation_mode_change` row after the summary.

- **Enforcement is immediate.** The `PreToolUse` guard and `canUseTool` read the live mode, so the next tool call follows it, child agents included. A call already past the guard finishes. Switching to Chat denies edit prompts still waiting for approval (`DecisionBroker.reconcileOperationMode`, with Claude's tool names).
- **Claude is told through the queue.** Each queued message ends with the mode Claude should apply from there: a switch notice (`claudeModeSwitchNotice`) if Claude has not been told, otherwise `CHAT_MODE_NOTE` in Chat mode. A switch with no queued message to carry it goes as its own `priority: 'next'` message, but only while a main-agent tool runs, so Claude reads it at that tool's boundary. With no tool running it waits for the next tool or queued message: sent alone, it would start an extra turn after `result`. An accepted ExitPlanMode needs no notice, since its tool result tells Claude.
- **Recorded where Claude read it.** When Claude starts a message that changed its mode, the orchestrator persists an `operation_mode_change` row there (above the user row, if one carried it) and emits `operation_mode_changed`. The rest of the turn continues below it, like a mid-turn queued message, so no response checkpoint is displaced. Queued user rows record the mode they were read in.
- **A switch Claude never read** (none of the above happened before the run ended) is still kept: every response row records `meta.operationMode`, so the final row carries the mode the run ended in, the composer restores it (`selectOperationMode`), and a queued successor run starts in it. Claude learns at the next message, from `CHAT_MODE_NOTE` or the run's Agent prompt.

Edge: a notice pushed in the instant a tool finishes can miss that boundary and start its own turn after `result`; Claude then replies to it. Switching never changes the tool list or the cached prefix (see Tools and permissions).

## Ultracode and background tasks

The composer popover's **Ultracode** switch (Claude only; it replaced the composer Orchestrator switch, which stays in Settings for Graviton's own subagents) is a renderer preference (`chat:claudeUltracode`). Each Claude request then carries `claudeUltracode: true`, and the session passes `ultracode: true` in its flag `settings`. Ultracode is session-scoped, so every run restates it. Claude may then hand work to its `Workflow` tool. Typing the word "ultracode" in a prompt has the same effect for one turn, through Claude's own keyword trigger. Workflows need an account with Workflows enabled and a model that supports them; Claude owns that check.

A `Workflow` call returns at once ("launched in background"), and the turn usually ends while the workflow runs. When the task ends, the CLI starts a new turn by itself to answer it. That turn opens with a fresh `system init` and has no user message. Its rows are children of the previous response, like a queued message's turn.

- **The session stays open while background work runs.** `background_tasks_changed` (non-ambient tasks, child agents' included) and the main agent's own task bookends decide it. Input and the queue stay open meanwhile, so a message sent during a workflow reaches Claude at once instead of waiting for the run to end. Once a task the main agent launched ends, the session waits up to 10 seconds for the turn that answers it. The CLI 2.1.314 probe also held a closed-input session open for a running workflow, but the SDK documents killing held tasks in that case, so Graviton does not rely on it.
- **Progress shows on the launching call.** `task_started` / `task_progress` / `task_updated` / `task_notification` fold into a `ClaudeBackgroundTask` (`applyClaudeTaskEvent`, `shared/claudeProvider.ts`) stored as `task` on that call's `tool_result` block. Progress writes are coalesced to one per second; start and end write at once. `ToolCallGroupCard` draws it with `BackgroundTaskView`: workflow name, each agent's state, the current step, then the completion summary and usage. `Workflow` calls stay outside collapsed Agent steps. Tasks of child agents (`owned_by_subagent`, on calls Graviton never projected) are not shown; they stay in Claude's transcript.
- **Stop ends them.** Stopping the run makes the CLI kill its background tasks. A task still marked running when the run ends is saved as `stopped`.
- **The composer shows what holds the run open.** The CLI's level signal (non-ambient tasks, child agents' and backgrounded shells included) is forwarded as a `background_tasks` SSE event (`turnActive`, `tasks`), published only while tasks exist and once more when the last ends. It is kept in the run snapshot, so a reconnecting client sees the current set. After `result` the renderer replaces "Composing" with "Waiting on N background tasks"; its popover stops one task (`POST /api/conversations/:id/streams/:streamId/tasks/:taskId/stop`, SDK `stopTask`) or tails a shell/Monitor task's last 8 KiB (`GET …/tasks/:taskId/output`, the runtime-only SDK `getTaskOutput`). A task can never outlive its run: a long-lived dev server started by Claude keeps the run open until it is stopped.

`scripts/test-claude-workflow-live.mjs` (opt-in, `CLAUDE_PROVIDER_LIVE_TEST=1`, `CLAUDE_WORKFLOW_SCENARIO=open|closed|keyword|slow-open|slow-closed`) prints the raw SDK task events. The opt-in service test `live service: an ultracode workflow keeps the session and queue open and shows its progress` checks the service path.

## Copied chats

Heimdall's New Chat From Here, Copy and Move never carry a native session to the copy. A Claude branch can be transferred only up to a committed summary; selections ending elsewhere are refused (see `agent_context/agent_heimdall.md`). Copied rows get `meta.transfer` and lose `claude.checkpoint`, and no checkpoint or `claude_branch_sessions` row is copied, so no copy can resume or append to the source session.

In the copy, every continuation from the copied summary is a summary handoff, whatever the provider: the composer sends it as a summary branch, and `runMessage` rewrites an ordinary `send` whose parent is a copied summary (directly or through trailing context rows) into the same branch (`copiedSummaryForSend`). It therefore always gets a new lineage, and a session left on the old lineage by an earlier run is never resumed. Claude starts a fresh session with the summary text; approval uses the host default, as other handoffs do. Messages copied from before the summary are display only: continuing from one is refused with "copied from another chat … continue from the copied summary instead", and Explain is disabled on them. Deletion may cut back to any copied row (`planMessageDeletion`), since none of them resumes a native session.

## Persistence

Migration 12 adds `claude_branch_sessions` (lineage, latest model, locked workspace, native session/state) and `claude_message_checkpoints` (Graviton row to native UUID). `messages.meta` records Claude provenance and existing model selection. API response blocks sharing a native `message.id` aggregate into one Graviton row; native tool results enrich the matching tool-owner row without creating competing execution.

## Native compaction projection and handoff

The SDK `PostCompact.compact_summary` callback captures the generated text; persistence waits for the ordered `compact_boundary` iterator event so buffered pre-compaction output cannot move below the summary. The lineage-aware sink inserts an assistant row tagged `kind: compaction_summary`, `state: committed`, with Claude session provenance, then emits the existing `context_compaction.completed` event. Native tools/reasoning are not replayed as executable history. Missing hook text or missing boundaries fail explicitly rather than publishing an unverified handoff. A summary is not a resumable assistant checkpoint; ordinary same-session continuation after idle manual compaction uses its matching native session, while an explicit summary branch starts fresh.

The `context_compaction.started` indicator follows the stream's `system status: 'compacting'` event, not the `PreCompact` hook. CLI 2.1.318 gives subagent contexts no compaction-event sink, so that status is main-thread only. It repeats every 30 seconds during a long compaction, and only the first one starts the indicator. A background agent's `PreCompact` cannot be told apart: it carries the parent's `session_id` and `transcript_path` and no `agent_id`. Before this change, a background agent compacting its own context showed the main chat as compacting, and the indicator never cleared. Graviton's own PreCompact hooks still run from that hook, so they may also run for a background agent's compaction. `PostCompact` is not sent for subagents. If a main turn reaches `result` with the indicator still set, it is cleared as failed ("Claude compaction did not complete").

Observed on installed CLI 2.1.310 and pinned SDK 0.3.309: native `/compact`, PostCompact callback with `disableAllHooks: true`, persisted service summary and immediate same-session recall passed with synthetic test sessions. Native `getSessionMessages` omits pre-compaction live-chain rows, but exact historical `forkSession(upToMessageId)` still works and excludes later-only context; missing cuts reject. `scripts/test-claude-compaction-live.mjs` provides opt-in SDK coverage; the opt-in `claudeSessionService` test exercises actual service projection. Automatic-compaction callback/order is regression-tested with SDK fixtures, not a live context-limit run. No private session JSONL parsing is used.
